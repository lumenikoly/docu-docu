# Контракт Agent Console

Контракт отделяет общий жизненный цикл coding agent от протокола конкретного
поставщика. Реализованные HTTP-схемы определяет
[Agent Console OpenAPI](agent-console.openapi.yaml); этот документ фиксирует
обязательное реализованное поведение и его границы.

## Сессия и ответ

Основной `serve` поддерживает не более одной активной Agent Session.
Необязательная связь с задачей, provider и настройки запуска становятся частью
identity сессии и не меняются до её завершения. Навигация Portal не должна
завершать сессию. Запуск другой задачи отклоняется, пока пользователь явно не
остановит связанную с первой задачей сессию.

Manager сериализует все операции, меняющие сессию. Сообщение в свободную сессию
начинает новый turn. Сообщение во время активного turn передаётся как steering,
если текущая сессия это умеет; определённый отказ или отсутствие steering
помещает сообщение в FIFO. Такое сообщение всегда начинает отдельный turn и
позднее не превращается в steering.

FIFO содержит не более 32 сообщений размером до 65 536 UTF-8 bytes каждое.
Переполнение отклоняет новое сообщение. Сообщение после принятия сохраняет ID,
текст, turn policy и время; для изменения пользователь отменяет его и создаёт
новое.

Снимок очереди передаёт stable ID, положение FIFO, состояние `queued` или
`not-sent` и необязательную нормализованную причину. Отмена принимает только ID,
сериализуется manager и возвращает новый authoritative snapshot. Frontend не
удаляет envelope оптимистически. `not-sent` никогда не отправляется повторно
автоматически.

`Stop response` прерывает только текущий turn и сохраняет FIFO. Если результат
interrupt неизвестен, manager не запускает очередь, переводит сообщения в
`not-sent` и требует остановить принадлежащее provider исполнение. `Stop agent`
завершает всю сессию; при pending messages обычная операция сначала возвращает
их количество и требует явного разрешения удалить все сообщения, актуальные на
момент повторного stop.

После подтверждённого interrupt первый queued envelope начинает новый turn, а
остальные выполняются по одному после завершения предыдущего. Manager никогда
не превращает их в steering.

Project Terminal не является AgentSession и доступен независимо от результата
structured integration. По явному действию он запускает стандартную командную оболочку в корне
репозитория. Agent Session и Project Terminal могут работать одновременно;
остановка, прерывание или ошибка одного жизненного цикла не меняют другой.

После crash pending messages переходят в `not-sent` и остаются частью failed
session, чтобы интерфейс мог их показать. Отдельный recovery store не создаётся.
Новая сессия запрещена, пока подтверждённый stop не очистит failed session и
сообщения `not-sent`. После cleanup продолжение задачи создаёт новый thread и
заново читает актуальный task context; старый thread не возобновляется.

Queue model различает только `queued`, `not-sent` и `cancelled`. Успешно
переданное как steering или новый turn сообщение больше не принадлежит очереди.
Неопределённая доставка является причиной состояния `not-sent`, а не отдельным
состоянием сообщения.

## Возможности provider и session

Общий контракт различает потенциальные возможности adapter
(`ProviderCapabilities`) и гарантии конкретной созданной сессии
(`SessionCapabilities`). Интерфейс и prepared actions используют гарантии
сессии. Например, `ReadOnlyTurns` доступна только тогда, когда adapter может
ограничить filesystem и затем точно восстановить базовую политику. Текстовая
просьба не заменяет это техническое ограничение.

Добавление structured provider с другой моделью разрешений не должно менять
AgentSession, очередь, task binding, stop semantics или общий контракт доступа.
Это архитектурный инвариант, который проверит интеграция следующего provider, а
не исполняемый критерий текущей задачи. Adapter владеет transport, provider
process и подтверждением его остановки; manager не знает PID, HTTP server или
PTY-механику.

## События

Общий поток различает пользовательское сообщение, ответ агента, состояние
turn, выполнение команды, изменение файлов, approval, завершение turn и ошибку
сессии. Он не содержит hidden reasoning или reasoning tokens.

После успешного принятия `message` transport публикует событие
`user_message` со стабильным `itemID` и исходным plain-text текстом. Поэтому
исходящее сообщение входит в тот же bounded replay, что и ответ агента, и
видно после reconnect, пока не вытеснено лимитом буфера. Принятое сообщение
сохраняет запись в хронологии и тогда, когда manager помещает его в `queued` или
`not-sent`; только отклонённая отправка не создаёт такое событие.

Выполнение команды имеет стабильный идентификатор, команду, при необходимости
рабочий каталог, поток ограниченного stdout/stderr, состояние, exit code и
duration. Agent View показывает компактную карточку вызова в хронологии
разговора; её нажатие открывает Command Output с read-only подробностями того
же идентификатора. Обрезание помечается явно и сохраняет доступный хвост для
reconnect.

Сообщения агента остаются plain text. Frontend сохраняет пробелы и переносы
строк, но не интерпретирует Markdown, HTML, ссылки или изображения. Command
Output также не является terminal: безопасный renderer разрешает только plain
text, переносы строк и SGR foreground/background, `bold`, `dim`, `underline` и
`reset`. Cursor movement, erase, alternate screen, OSC hyperlinks, clipboard,
bell, device queries и остальные control sequences удаляются без действия.

Адаптеры Codex и OpenCode преобразуют собственные сообщения в общий
`AgentEvent`. OpenCode читает server-sent events, восстанавливает соединение
после разрыва и передаёт текст, команды и их вывод, изменения файлов,
завершение ответа и ошибки. Неизвестное событие поставщика игнорируется; типы
его протокола не входят в общий `AgentProvider`.

## Доступ и approvals

Пользователь выбирает вне репозитория один из поддержанных provider режимов
запуска. `Default` сохраняет configuration chain provider без access overrides.
`Full access` выражает намерение запросить максимальный доверенный режим,
который adapter умеет корректно применить; managed и explicit deny policies не
обходятся.

Общий слой хранит requested preset и сводку фактического доступа
`EffectiveAccessSummary {known, unrestricted}`. Неизвестный результат никогда
не показывается и не используется как подтверждённый неограниченный доступ.
`unrestricted=true` разрешён только тогда, когда adapter доказал отсутствие
релевантных provider-enforced ограничений. Конкретные sandbox, approval и
permission rules остаются внутри adapter.

Предпочтение хранится в user-local state отдельно для canonical repository root.
Первое включение `Full access` требует подтверждения для этого репозитория.
Повреждённый или несовместимый объект целиком игнорируется в пользу `Default` и
не перезаписывается без явного reset. Изменение предпочтения во время сессии
применяется только к следующей сессии.

Codex `Default` не передаёт access overrides. `Full access` передаёт
`sandbox=danger-full-access` и `approvalPolicy=never`. Codex adapter хранит полный
типизированный базовый `SandboxPolicy`: filesystem-read-only turn передаёт
`readOnly`, а следующий обычный `turn/start` передаёт точную исходную policy
вместе с сообщением, поскольку turn override действует и дальше. Если точное
восстановление невозможно, adapter отклоняет обычный turn и сессия объявляет
`ReadOnlyTurns=false`. Эта capability гарантирует read-only filesystem sandbox,
но не заявляет отсутствие side effects через MCP, apps или другие внешние
permission surfaces.

OpenCode `Default` также не меняет пользовательскую конфигурацию. Для `Full
access` сервер Toudocu добавляет только в окружение принадлежащего ему процесса
`opencode serve` правило `OPENCODE_PERMISSION={"*":"allow"}`. Запрошенный
режим остаётся виден как `Full access`, но сводка не называет доступ доказанно
неограниченным: adapter не проверяет остальные ограничения OpenCode. Он
объявляет `Interrupt`, но
не объявляет steering, approvals и turns только для чтения: совместимый
структурированный контракт этих возможностей сейчас не подтверждён.

Browser и файлы репозитория не задают executable, argv, cwd или access policy.
Approval показывается и разрешается отдельным structured действием, а не вводом
в Command Output.

При запуске Project Terminal доверенная серверная часть выбирает стандартную
командную оболочку платформы. Браузер передаёт только действие запуска, ввод и
размер терминала. Все команды после запуска оболочки вводит сам пользователь;
Toudocu не предлагает отдельного действия для Codex и не трактует команды как
действия агента. После запуска PTY браузер повторно передаёт вычисленный размер,
чтобы полноэкранные TUI получили ненулевую геометрию.

Текущий снимок сессии, а не история событий, является источником актуальных
pending approvals. Снимок передаёт только ожидающие запросы со стабильными IDs;
ответ по ID идемпотентен. Поэтому обработанный запрос не появляется снова после
reconnect, даже если исходное событие сохранилось в bounded replay.

## Остановка provider

Manager использует один идемпотентный lifecycle для явного stop, shutdown,
startup rollback и аварийного cleanup. Сначала он запрещает новые операции и
разрешает судьбу pending messages, затем вызывает `ProviderSession.Stop()`.
Adapter выполняет graceful shutdown, закрывает transport, ждёт внутренний grace
period и при необходимости завершает принадлежащее ему дерево процессов.

Подтверждённая остановка переводит сессию в `exited`. Если adapter не может
подтвердить прекращение исполнения, сессия остаётся `failed` с причиной
`provider_stop_unconfirmed`, а новую сессию запускать нельзя.

## Действия задачи

Agent Console не определяет доступность, инструкцию или изменение Markdown для
действий задачи. Он принимает готовую инструкцию от
[Task Actions](task-actions.md), проверяет связь с задачей и применяет требуемую
политику ответа. Проверка задачи и Agent Feedback остаются отдельными явными
операциями Agent Console.

Install или update Toudocu skill остаются отдельными подтверждёнными действиями,
но состояние skill не блокирует запуск Agent Session или подготовленного
workflow и не выводится как обязательная ручная проверка в Agent View.

Setup projection сообщает `availableProviders`, выбранный provider, preference
следующей сессии, а также доступные выбранному provider модели с
поддерживаемыми уровнями reasoning и
состояние skill. Один доступный provider отображается как
read-only значение; selector нужен только при двух и более элементах. Сервер
передаёт готовые diagnostics и CLI-инструкции: browser не конструирует их из
внутренних состояний installer.

## Режимы публикации

Agent API и transport существуют только в основном `serve`,
привязанном к loopback-адресу. Статическая сборка, порталы переводов и любой
`serve` на адресе, который не является loopback, не должны получать возможность
агента, endpoints или право запустить внешний процесс; `--host 0.0.0.0` служит
лишь одним примером запрещённой привязки.

## Транспорт основного `serve`

Основной `serve` на loopback-адресе публикует
[Agent Console OpenAPI](agent-console.openapi.yaml). `PageBootstrap v1`
объявляет `capabilities.agentConsole` и `endpoints.agentConsole`; статическая
сборка, переводной портал и сервер на сетевом адресе не получают эти поля и
маршруты.

Проекция и выполнение действий задачи принадлежат отдельному
[Task Actions OpenAPI](task-actions.openapi.yaml) и не входят в маршруты
управления Agent Session.

HTTP-запросы запуска и остановки принимают только заранее определённые поля,
требуют заголовок `X-Toudocu-Action` и подтверждение того же origin. Рабочий
каталог и исполняемый файл выбирает Go-процесс: браузер не передаёт `cwd`,
`executable`, `argv` или environment. Сервер также требует loopback-значение в
HTTP `Host`, поэтому совпадение двух подставленных внешних доменов в `Host` и
`Origin` не даёт доступ к операциям агента.

WebSocket передаёт нормализованные `AgentEvent`, снимки состояния и вывод PTY,
который Toudocu не интерпретирует. В обратную сторону transport принимает
ограниченные структурированные действия агента либо ввод, изменение размера и
прерывание терминала; отдельной кнопки прерывания терминала в интерфейсе нет.
Каждое серверное сообщение получает монотонный `sequence`.
При повторном подключении параметр `since` возвращает доступный хвост в пределах
3 МиБ; более старые данные намеренно не сохраняются. Снимок состояния не раскрывает браузеру рабочий каталог, имя
поставщика или его внутренний протокол. При завершении `serve` подписка,
подключения и временный буфер освобождаются вместе с Agent Session.

Если live-подписчик не успевает принимать сообщения и его очередь заполняется,
transport закрывает WebSocket вместо молчаливой потери события. Browser
подключается снова с последним подтверждённым `sequence` и получает только
события, ещё сохранённые в bounded replay. Frontend объединяет соседние
текстовые дельты одного элемента перед обновлением представления, не меняя
порядок событий завершения.

Если `since` старше доступного хвоста, transport явно сообщает replay gap.
Frontend не выводит gap из разницы sequence и показывает один нейтральный
разделитель для конкретного пропуска. Потеря bounded history не является
ошибкой сессии.

При временном disconnect browser сохраняет последнюю проекцию как потенциально
устаревшую, блокирует изменяющие действия и reconnects с последним
подтверждённым sequence. Authoritative snapshot после reconnect разрешает
действия снова. Закрытие или размонтирование Console не останавливает
server-side Agent Session. При изменении документации или ручной пересборке
`serve` заменяет содержимое портала через мягкую навигацию и сохраняет текущий
экземпляр Agent Console, поэтому его локальная история не сбрасывается.

## Представление Agent Console

В основном `serve` иконка Agent Console в заголовке показывает и скрывает
постоянную правую панель и служит единственным явным действием закрытия.
Доступное имя иконки сообщает состояние агента, а
badge появляется только при ожидающих approvals. Отдельная иконка Project Terminal так же показывает и скрывает
интерактивный терминал в этой панели, не останавливая его процесс. В заголовке
панели одна иконка запускает или останавливает терминал; отдельные действия
закрытия панели и отправки `Ctrl+C` в режиме терминала отсутствуют. Project
Terminal и Agent Session могут работать одновременно. На широком экране заголовок остаётся во всю
ширину окна, а панель резервирует свою ширину только для основного содержимого:
оно сжимается и не оказывается под Console. Пользователь может перетаскивать
левую границу Console и менять её ширину с клавиатуры; выбранная ширина локально
сохраняется и одинакова для Agent View и Project Terminal. Agent View и Command Output
доступны как две управляемые с клавиатуры вкладки, поэтому разговор и
технический вывод не конкурируют за ширину. Console, мобильное меню и ручное сворачивание левой навигации на
широком экране используют одинаковые длительность и кривую плавности, кроме
режима `prefers-reduced-motion`. На узком экране панель занимает ширину под
заголовком, показывает две доступные с клавиатуры вкладки и делает фоновое
содержимое неактивным. Console не меняет состояние левой навигации: её можно
свернуть, развернуть или изменить её ширину отдельным разделителем на широком
экране; выбранная ширина также сохраняется локально. Повторное нажатие на иконку или Escape возвращает фокус
к открывшей панель кнопке.

Только открытие Project Terminal загружает xterm JS/CSS; static runtime и обычный
structured режим не загружают эти assets.

При soft navigation между обычными страницами портала React root Console
сохраняется: панель не переоткрывается и не теряет локальное UI-состояние.
Другие островки страницы по-прежнему могут размонтироваться. При полной
навигации `open` и `activeTab` восстанавливаются из `sessionStorage`; сессия,
входящие и принятые исходящие сообщения, команды, очередь, approvals и access
snapshot остаются server-side в пределах bounded replay.

Command Output по умолчанию следует за последней выполняемой командой. Ручной
выбор карточки выключает `followLatest`; новые команды показывают ненавязчивое
уведомление и действие `Follow latest`, которое выбирает текущую выполняемую
или последнюю команду. Pending messages отображаются в порядке FIFO над
composer.

Под полем сообщения пользователь выбирает модель и поддерживаемый ею уровень
reasoning. Agent Console получает каталог Codex через `model/list`, а каталог
OpenCode — вместе с вариантами reasoning через `opencode models --verbose`;
сохраняет выбор для корня репозитория и передаёт `model` и `effort` при запуске
ответа. Адаптер OpenCode передаёт сохранённый `effort` как поле `variant` его
HTTP API. Если сохранённый выбор отсутствует в
каталоге, Console показывает реальную модель, отмеченную provider как default,
или первую доступную модель, а для неё — объявленный default reasoning. Если
каталог не сообщает уровни reasoning, соответствующий селект не показывается.
Выбор provider находится
в строке вкладок Agent View и Command Output. Модель, reasoning и небольшой
переключатель доступа находятся в нижней toolbar внутри composer;
после запуска сессии настройки блокируются. Отправка, запуск, остановка и
служебные действия представлены подписанными для assistive technology иконками.
Первое нажатие `Stop agent` разворачивает его в два значка: возврат отменяет
действие, а подтверждение отправляет остановку. Это защищает сессию от
случайного завершения, не меняя отдельное предупреждение об удалении pending
сообщений.

Новое approval не меняет вкладку автоматически. Badge и сообщение `aria-live`
делают его заметным на узком и широком экране. При остановке с pending messages
typed conflict показывает отдельное количество `queued` и `not-sent`; после
подтверждения повторный stop удаляет все pending, существующие на момент
серверной обработки. После начала stop новые сообщения отклоняются с
нормализованной причиной `session_stopping`.

Пока у сессии есть активный ответ (`activeTurn`), Agent View показывает
текстовый индикатор работы. Если provider объявил capability `interrupt`, рядом
доступно действие `Stop response`. Событие завершения ответа убирает индикатор
и действие, не завершая Agent Session.

Кнопка Agent Console переливается цветом, пока активный ответ выполняется, и
переходит в монотонное состояние после его завершения. Ожидающие решения
approval обозначаются знаком `!` на кнопке, без числового счётчика.

Когда сессия не активна, отдельное действие Agent View открывает до 50 последних
нативных Codex threads для канонического корня репозитория. Новый запуск создаёт persistent
thread, а `Resume` использует `thread/resume`: Toudocu не копирует и не хранит
транскрипт. Перед восстановлением adapter читает thread и требует точного
совпадения его `cwd` с корнем текущего репозитория. Восстановление отклоняется,
если другая Agent Session уже активна.

Failed session показывает нормализованную причину, `not-sent` и действие
cleanup, но не предлагает restart до подтверждённой остановки. Причина
`provider_stop_unconfirmed` блокирует новую сессию. Изменение access preference
во время активной сессии явно относится только к следующей сессии. Модель и
reasoning изменяются только до запуска новой сессии.

## Реализованная основа

`internal/app/agent_provider.go`, `agent_events.go`, `agent_session.go` и
`agent_codex.go` содержат общий менеджер, контракты и первый адаптер. Transport
в `agent_console_http.go` скрывает протокол поставщика от браузера. Адаптер
находит `codex` через доверенный поиск
исполняемого файла, запускает напрямую `codex app-server --stdio`, выполняет
`initialize` и `initialized`, создаёт или восстанавливает persistent thread и
поддерживает start, steering и interrupt для turn. Перед созданием сессии отдельное короткое подключение
получает каталог `model/list`; рабочая сессия передаёт сохранённые `model` и
`effort` в `turn/start`. Agent Console отображает эту сессию через Agent View и
Command Output. Отдельная иконка заголовка открывает Project Terminal
независимо от structured integration; PTY и Agent Session могут работать одновременно.
