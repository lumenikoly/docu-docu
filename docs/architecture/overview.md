# Архитектура

Toudocu помогает вести документацию как целостную модель проекта, а не как
набор разрозненных Markdown-файлов. Он связывает архитектуру, требования и
рабочие задачи, проверяет их структуру и согласованность, а затем показывает
результат в удобном портале. Люди работают с HTML, автоматизация — с CLI и
JSON, а Go-программы — с публичным API. Всё обрабатывается локально в одном
исполняемом файле; браузер отвечает только за интерактивность.

Команда `serve` открывает портал на локальном HTTP-сервере и добавляет редактор
исходных файлов и справку по внутреннему API. Только этот локальный портал может
один раз запросить у GitHub номер последнего стабильного релиза. Для остальной
работы Toudocu не нужны база данных, CDN или внешний сервис.

## Граница системы

Разработчик, CI или Go-программа передаёт Toudocu путь к документации и, при
необходимости, корень репозитория. Toudocu читает Markdown, локальные ресурсы и
распознанные OpenAPI-контракты, а затем возвращает список ошибок или создаёт
HTML- и JSON-файлы. В локальном режиме `serve` разработчик может сам открыть
Project Terminal: Toudocu создаёт системный терминал (PTY/ConPTY) и запускает
обычную командную оболочку в корне репозитория.
Последующие команды вводит пользователь. Браузер не задаёт исполняемый файл,
аргументы, рабочий каталог или окружение. Терминал проекта и структурированная
сессия агента имеют независимые жизненные циклы.

Портал после `build` доступен только для чтения. При `serve` браузер может
отправить разрешённое изменение файла, после чего Go-процесс заново читает
документацию и перестраивает портал. Команды проекта запускает только явно
выбранная проверка задачи. Запрос сведений о релизе можно отключить; он не
загружает исполняемый код и отсутствует в статическом и переводном порталах.
