# Использование навыка Toudocu

Установленный навык помогает агенту работать с исходной документацией,
порталом и задачами проекта. Он не заменяет программу Toudocu: команды терминала и
сообщения агенту — два разных интерфейса.

## Команда терминала и сообщение агенту

`toudocu skill ...` управляет только установленной копией навыка:

```bash
toudocu skill install
toudocu skill status --agent all
toudocu skill update --agent codex
toudocu skill uninstall --agent codex
```

`$toudocu ...` пишется в сообщении агенту разработки:

```text
$toudocu проверь исходную документацию и объясни ошибки
$toudocu собери локальный портал в принятом проектом каталоге
$toudocu подготовь контекст TASK-AREA-001
$toudocu обнови руководство по текущему CLI-контракту
$toudocu clarify миграцию формата конфигурации
$toudocu feedback
```

Go CLI предоставляет `check`, `build`, `serve`, `changes`, `agent`, `search`,
`scaffold`, `task`, `skill` и `version`. Команд `init`, `refresh`, `translate`
и `clarify` в нём нет: это процессы агента. Обратная связь с агентом, напротив,
использует реальные команды `agent next|respond`. В исходном репозитории самого
Toudocu агент запускает CLI через `go run ./cmd/toudocu`; в установленном
проекте — бинарник `toudocu` из `PATH`.

## Обычные поручения

Специальное слово не обязательно. Навык подходит, когда нужно:

- найти документ, проверить структуру или объяснить сообщение Toudocu;
- собрать статический портал или запустить его локально по правилам проекта;
- создать или уточнить подтверждённый источник: руководство, контракт, ADR,
  модуль, сценарий, процесс, экран, дорожную карту, риск или рабочую задачу;
- получить контекст `TASK-*`, проверить полноту контракта, показать план команд
  или выполнить отдельно разрешённую проверку;
- обновить конкретную документацию по подтверждённому коду, поведению или
  решению без полного обзора проекта.

Перед действием агент читает инструкции репозитория, применимые стандарты и
существующие эксплуатационные инструкции. Он использует найденные пути документации и репозитория,
исключения, срок устаревания и выходной каталог. Если проект ничего не задал,
запасной вариант — `./docs` и его родитель как корень репозитория.

`toudocu check` подтверждает структуру, ссылки и объявленные связи. Он не может
доказать, что текст полезен, правдив или написан для нужного читателя.

## Что требует отдельного разрешения

Просьба «проверь» или «объясни» не разрешает менять файлы. Просьба обновить
конкретный документ разрешает этот документ и необходимые согласованные ссылки,
но не весь проект.

| Действие | Когда оно разрешено |
|---|---|
| `$toudocu init` | Пользователь явно вызвал `init` или однозначно попросил именно инициализацию |
| `$toudocu refresh` | Пользователь явно запросил полный обзор и обновление всей исходной документации |
| `$toudocu refresh diff` | Пользователь явно запросил актуализацию текущих Git-изменений и зависимых документов |
| `$toudocu translate <locale> ...` | Пользователь явно назвал перевод и целевую локаль |
| `$toudocu translate diff` | Пользователь явно разрешил обработать текущий diff для всех настроенных переводов |
| `$toudocu clarify <subject>` | Пользователь явно попросил Toudocu провести проясняющее интервью до общего понимания |
| `$toudocu feedback` | Пользователь явно разрешил обработать только доставки из локальной очереди обсуждений |
| `task verify --run` | Пользователь явно разрешил выполнить команды доверенной задачи |

Отсутствующие файлы, первое использование навыка, обычная правка или запуск
`check` не разрешают `init`. Просьба обновить одно руководство не разрешает
полный `refresh`. `task context`, `task ready`, `task candidates` и
`task verify --dry-run` не исполняют команды; `--run` исполняет код репозитория
с правами текущего пользователя.

Задача `TASK-*` создаётся только по явному требованию пользователя или проекта
либо когда существенной работе действительно нужен долговечный контракт:
область, критерии, проверка и передача между исполнителями. Небольшая правка или
обычный вопрос отдельной задачи не требуют.

## Повседневная работа

### Найти и проверить

Для машинного анализа агенту удобен JSON, для человека — обычный текст:

```bash
toudocu check ./docs --repository-root . --format json
toudocu check ./docs --repository-root .
toudocu search "verification" ./docs --format json
```

Ошибки всегда дают неуспешный результат. `--strict` дополнительно делает
предупреждение причиной ненулевого кода и используется только по политике
проекта, CI или явной просьбе.

### Собрать или открыть портал

`build` записывает производный каталог, а `serve` сначала собирает его, затем
запускает локальный HTTP-сервер. Агент использует принятый проектом выходной
путь либо отдельный временный каталог. Перед `--clean` он убеждается, что путь
не является исходной документацией, её родителем, системным корнем или опасной
символической ссылкой.

Каталоги `build/`, `dist/`, `project-docs/` и другой собранный портал никогда
не редактируются как источник документации.

`serve` по умолчанию слушает `127.0.0.1`. Режим `0.0.0.0` разрешается только
по отдельной просьбе для доверенной сети: встроенных TLS и авторизации нет.
Явные действия браузера могут сохранить файл, создать новый разрешённый файл
или добавить результат в дорожную карту. Флаг `--no-update-check` отключает
единственный запрос метаданных релиза к GitHub.

### Работать с существующей задачей

Для задачи со статусом «Готово к работе» или выше агент сначала получает
контекст только для чтения:

```bash
toudocu task context TASK-AREA-001 ./docs \
  --repository-root . \
  --format json
```

План команд также сначала читается без запуска:

```bash
toudocu task verify TASK-AREA-001 ./docs --dry-run \
  --repository-root . \
  --format json
```

`--run` допустим только после отдельного разрешения, в доверенном репозитории и
после проверки локального контракта задачи. JSON-отчёт сохраняется вне исходной
документации. Архивирование и восстановление выполняются командами
`task archive` и `task restore`, а не ручным переносом.

### Изменить обычный документ

Агент определяет читателя, вопрос документа и реальный источник истины. Он
обновляет существующий документ вместо дубликата и не придумывает неизвестные
статусы, даты, связи и процедуры. Тип документа выбирается по его
назначению, а не ради ID или успешной проверки.

После правки обычно есть два последовательных этапа:

1. Смысловая вычитка: полезность, доказательства, границы, отсутствие
   противоречий и правильное место информации. Изменение требований,
   архитектуры, контрактов, статусов, стабильных ID и машинных связей требует
   независимого рецензента.
2. Структурная проверка всего проекта через `check`. `--strict` добавляется
   только по правилам проекта или просьбе пользователя.

Если пользователь запретил проверки, агент не запускает их и честно сообщает
об этом. Связь нельзя удалить, а неподтверждённый текст — добавить только ради
чистого отчёта.

## Специальные процессы

### Прояснить изменение до реализации

`$toudocu clarify <subject>` нужен, когда до реализации следует глубоко
проработать задачу, функцию, архитектурное решение, миграцию или контракт. Этот
процесс запускается только явно: обычная просьба изменить код или документацию
не превращается в интервью.

До первого вопроса агент собирает факты. Для существующей `TASK-*` или `BUG-*`
со статусом «Готово к работе» или выше он начинает с
`task context --format json`, а для свободной темы — с `toudocu search`.
Найденные документы задают начальный контекст; затем агент читает только
необходимый код, тесты, схемы, конфигурацию, CI и другие авторитетные источники.
Текущее поведение, значения по умолчанию и существующие связи — это факты,
которые агент проверяет сам. Пользователю остаются решения о будущем поведении,
совместимости, границах, приоритетах и компромиссах.

Агент ведёт внутреннее дерево решений. В каждом раунде он задаёт весь текущий
фронтир — все независимые вопросы с уже известными фактами и разрешёнными
предпосылками. Число вопросов и раундов не ограничивается. Зависимый вопрос
появляется только после ответа на предшествующий, а ставшая ненужной ветвь
удаляется. При необходимости агент отдельно проверяет терминологию, границы,
отрицательные требования и существенные сценарии ошибок.

Пустой фронтир ещё не завершает процесс. Агент кратко излагает подтверждённые
решения, исключения, ограничения, намеренно открытые вопросы и документы,
которые должны измениться, после чего ждёт явного подтверждения пользователя.
Исправление этой сводки снова открывает нужные ветви интервью.

После подтверждения долговечные решения записываются в существующие
канонические документы Toudocu, которым принадлежит соответствующее поведение
или правило. Универсальный `CONTEXT.md` и журнал интервью не создаются. `ADR-*`
допустим только для решения, которое одновременно трудно отменить, выглядит
неожиданным без контекста и выбрано из реальных альтернатив. После изменения
документации выполняется обычный `check`. Реализация, миграция продукта,
`task verify --run` и автоматический переход к разработке в этот процесс не
входят.

### Обработать только локальную очередь обсуждений Toudocu

До чтения документации, roadmap, `UC-*`, `TASK-*`, критериев приёмки или
статуса агент вызывает `toudocu agent next --json`. Ответ этой команды —
единственный источник работы: пользовательский промт не поручает искать
незавершённые задачи в репозитории. При `pending=false` агент останавливается,
не читая и не меняя файлы.

Для полученной доставки агент перечитывает цель, историю обсуждения, нужный Git
diff и минимальный контекст запроса. Для `question` он отвечает без изменения файлов. Для
`change_request` он меняет `target.path` и только однозначно названные
пользователем дополнительные пути, если они входят в безопасную границу вида
цели. Неоднозначный дополнительный путь требует ответа `needs_clarification`.

Один `AgentResponse` имеет результат `answered`, `changed`, `no_change`,
`needs_clarification` или `failed` и передаётся через `toudocu agent respond`.
Ответ обязателен до перехода к следующей записи или выхода. Для результата
`changed` сообщение прямо подтверждает внесённые правки и перечисляет все
`changedPaths`. После успеха доставка завершена, даже если обсуждение открыто;
новую работу создаёт только новое сообщение пользователя. Затем агент снова
вызывает `next`, пока не получит `pending=false`.

Внутри этого процесса агент не запускает `check`, тесты, lint, build и другие
команды проверки. Он также не обновляет по собственной инициативе связанные
документы, журнал изменений, сгенерированные файлы или соседний код.

### Инициализировать документацию

`$toudocu init` запускается только явно. До записи агент проверяет инструкции
репозитория, существующие документы, конфигурацию и управляемый блок корневого
`AGENTS.md`. Один маркер без пары, дубликат, неверный порядок или вложенность
блокирует изменение. Конфликтующая пользовательская инструкция и прежние
неструктурированные Markdown-файлы в `architecture/` также требуют ручного
решения.

При безопасном результате создаются только отсутствующие минимальные
`index.md` и `architecture/overview.md`, заполняются язык проекта и карта 12
встроенных разделов и добавляется либо обновляется управляемая инструкция.
Процесс не придумывает сущности и не создаёт задачу. Это не команда Go CLI и
она не запускается автоматически из-за отсутствующего файла.

Пути берутся из найденных корней и не обязаны называться `docs`. Для языка,
который не относится к `en-*` или `ru-*`, до записи нужна полная карта названий
12 разделов и явный выбор английского или русского набора служебных текстов.
Заголовок нового встроенного `index.md` берётся из итоговой карты разделов.

### Обновить всю исходную документацию

`$toudocu refresh` сопоставляет каждый Markdown-файл основного каталога с
кодом, публичными интерфейсами, схемами, конфигурацией, CI, решениями и
подтверждёнными требованиями. Каждый документ получает внутреннюю оценку:
актуален, требует правки, нельзя подтвердить, устарел, дублируется или лежит не
на своём месте.

Меняются только подтверждённые утверждения. Неоднозначность остаётся явной
нерешённой находкой. После редакторской работы выполняются смысловая вычитка и
проверка структуры, если пользователь их не запретил.

`refresh` не выполняет `init`, не устанавливает управляемые инструкции и не
строит новое дерево документации. Дата документа меняется только вместе с его
содержанием или связями. Поле `Last verified` эксплуатационной инструкции
обновляется лишь после реального прохождения процедуры.

### Обновить документацию текущего diff

`$toudocu refresh diff` требует рабочее дерево Git и существующий `HEAD`.
Начальный список включает изменения в индексе и вне его и новые файлы:

```bash
git diff --name-only HEAD --
git ls-files --others --exclude-standard
```

Затем добавляются зависимые документы: прямые и обратные ссылки, стабильные ID,
связи задачи, объявленные пути репозитория и изменившееся публичное поведение.
Собранные файлы, кэши, встроенные сторонние ресурсы и каталоги переводов
исключаются. Если Git или `HEAD` недоступен, процесс останавливается и предлагает
полный `refresh`, не расширяя область молча.

### Перевести документацию

Для одной локали нужно явно выбрать ровно один режим:

```text
$toudocu translate <locale> --task TASK-ID
$toudocu translate <locale> --base REF
$toudocu translate <locale> --all-stale
```

`$toudocu translate diff` не принимает локаль или дополнительный режим. Он один
раз получает текущие изменения основного каталога:

```bash
toudocu changes ./docs --base HEAD --target working-tree \
  --translation-input --format json
```

Затем все заранее настроенные профили проверяются до первой записи и
обрабатываются по одному в стабильном порядке. Процесс не создаёт и не дополняет
профиль. Пустой diff ничего не меняет. Ошибка одной локали сохраняет её прежний
манифест, но не мешает обработать остальные.

Перевод поддерживает тот же набор читательских файлов, что и основной каталог.
ID, команды, пути, URL, якоря, блоки кода и машинные контракты не переводятся.
Двоичные ресурсы копируются без изменения. Переведённые рабочие задачи — только
читательское зеркало: они не используются для контекста, готовности, запуска
проверок и записи редактора.

Перед обновлением манифеста сравниваются пути, типы документов, состояния и
смысл дорожной карты, затем выполняется строгая проверка выбранной локали. При
несовпадении или ошибке манифест остаётся прежним.

## Изоляция переводов

Основной каталог документации — единственный источник для обычного поиска по
репозиторию, инвентаризации, смысловой вычитки, анализа реализации и контекста
задач. Каталоги переводов из этих операций исключаются и не добавляются в
`.gitignore`.

Конкретный перевод читается только при явном `$toudocu translate <locale>` или
прямой просьбе проверить, найти, собрать, запустить или изучить эту локаль.
`translate diff` разрешает последовательно открыть все настроенные переводы.
За один раз читается одна минимальная пара исходного и целевого файла; сначала
сравниваются пути, хеши и структурные отчёты.

## Что должно быть в ответе агента

Агент перечисляет изменённые исходные файлы, переводы и манифесты. Для `init`
он отдельно называет конфигурацию и управляемый блок `AGENTS.md`. Для `refresh`
— просмотренную область, доказательства, нерешённые находки и изменения дат.
Для перевода — режим, локаль, паритет и состояние манифеста; для
`translate diff` — базу `HEAD` и отдельный результат каждой локали.

Также сообщаются результат авторской и, когда обязательна, независимой
смысловой вычитки, исправленные ошибки, оставшиеся предупреждения и фактически
применённая политика проверок. Не запущенные сборка портала и
`task verify --run` называются прямо.
