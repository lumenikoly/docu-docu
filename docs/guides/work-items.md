# Рабочие задачи

Каждая задача хранится в отдельном файле `work/*.md`. Функциональность,
обслуживание, документация и исследования используют ID `TASK-*`, ошибки —
`BUG-*`. В отчётах оба вида называются `WorkItem`: у них общие статусы,
зависимости, команды контекста и проверки и годовой архив.

## Минимальный черновик

В одном файле находится ровно одна задача:

```md
<!-- toudocu
id: TASK-AUTH-014
status: draft
taskType: feature
-->

# TASK-AUTH-014: Добавить восстановление пароля

<!-- toudocu:section result -->
## Результат

Пользователь может запросить ссылку для восстановления пароля.
```

Черновику нужны канонические поля `id`, `status`, `taskType` и непустой раздел,
помеченный как `result`. Остальные поля появляются по мере уточнения.

## Когда задача действительно нужна

Не создавайте `TASK-*` для каждого сообщения, вопроса, чтения кода,
форматирования, небольшой локальной правки или рефакторинга без нового
поведения.

Отдельная задача оправдана, если её требует пользователь или правила проекта
либо если большой работе нужен долговечный договор: чёткие границы, критерии,
команды проверки и передача между исполнителями. Это обычно изменение
контракта или архитектуры, миграция либо многошаговая функциональность. Если
подходящая готовая задача уже есть, используйте её вместо дубликата.

`$toudocu init`, `$toudocu refresh`, `$toudocu refresh diff` и
`$toudocu clarify` не создают задачу автоматически. Они применяют тот же порог.

## Статусы

| Статус | Когда ставить | Что дополнительно требуется |
|---|---|---|
| `draft` | Задача ещё уточняется | Тип и наблюдаемый результат |
| `ready` | Контракт согласован | Все рабочие разделы и проверки `AC-*` |
| `in-progress` | Изменения выполняются | Те же требования, что у готовой задачи |
| `blocked` | Работу нельзя продолжать | Непустой раздел с видом `blocker` |
| `done` | Результат принят | Все `AC-*` отмечены; есть `ALL` и `DOCS`; зависимости завершены |
| `cancelled` | Задача больше не нужна | Непустой раздел с видом `cancellation-reason` |

Другие написания и переводы не распознаются как машинные значения.

## Типы

Тип объясняет характер работы, а не её состояние.

| Тип | Смысл | Поле `useCase` |
|---|---|---|
| `feature` | Новая или изменённая пользовательская возможность | Обязательно |
| `bug` | Исправление наблюдаемой ошибки | Обязательно, кроме технического случая ниже |
| `maintenance` | Рефакторинг, инфраструктура или обслуживание | Необязательно |
| `documentation` | Изменение документации | Необязательно |
| `research` | Исследование или проверка гипотезы | Необязательно |

Для технического типа без `useCase` нужен раздел с машинным видом
`use-case-omission-reason`. Если `UC-*` указан, он должен существовать.

`task init --type Bug` создаёт `work/BUG-AREA-NNN.md`; остальные типы получают
`TASK-AREA-NNN`. Машинное значение `bug` требует префикс `BUG-`, а `BUG-*`
нельзя использовать для другого типа.

## Поля задачи

| Поле | Правило |
|---|---|
| `status` | Обязательно всегда; одно из значений выше |
| `taskType` | Обязательно всегда |
| `module` | Обязателен с `ready`; `MOD-*` должен существовать |
| `useCase` | Обязателен для `feature` и пользовательского `bug`; `UC-*` должен существовать |
| `flow` | Необязательный существующий `FLOW-*`; попадает в контекст задачи |
| `standards` | Необязательные существующие `STD-*`; требуют цель `QUALITY` |
| `runbooks` | Необязательные существующие `RB-*`; попадают в контекст |
| `parentTask` | Необязательный единственный `TASK-*`; означает декомпозицию |
| `dependsOn` | `TASK-*` и `BUG-*`, разделённые запятой |
| `priority` | Приоритет в канонической форме |
| `updated` | Необязательная ISO-дата для проверки устаревания |

ID уникален во всём `work/**`, включая архив. Зависимость должна существовать и
не образовывать цикл. Задачу нельзя завершить раньше её зависимостей.

## Декомпозиция большой задачи

Если существенная работа больше не помещается в один компактный и независимо
проверяемый рабочий элемент, разделите её на `TASK-*` по наблюдаемым результатам.
Поле `parentTask` отвечает на вопрос «частью какой общей работы является
задача». Поле `dependsOn` независимо задаёт порядок завершения.
Родительская связь сама по себе не определяет порядок выполнения соседних
дочерних задач.

До создания файлов составьте полное дерево и граф зависимостей. Сначала
создайте корневую родительскую задачу: `task init --parent` принимает только
существующего родителя. Затем создавайте потомков так, чтобы каждый родитель
появлялся раньше своих детей, а каждая зависимость получала меньший ID, чем
зависящая от неё задача. Для независимых задач сохраняйте порядок согласованного
плана, а при зависимости между ветвями сначала создавайте ветвь-предпосылку.
Так естественная сортировка ID в `task tree` и портале остаётся близкой к
порядку выполнения. При этом каждую реальную зависимость по-прежнему нужно
явно записывать в `dependsOn`: номер задачи не создаёт связь.

Дочерние задачи вычисляются по полю родителя; отдельного поля `Children` в
Markdown нет. Родитель должен существовать в `work/**`, включая архив, быть
`TASK-*` и не создавать цикл. Объединённый граф также не допускает взаимную блокировку,
когда родитель ждёт ребёнка, а ребёнок зависит от родителя.

Каждая задача начиная с «Готово к работе» сохраняет собственный результат,
границы, критерии, план, проверки и влияние на документацию. Выполненный
родитель требует статуса «Выполнено» у всех непосредственных детей; отменённый
ребёнок не считается выполненным. У отменённого родителя не остаются активные
дети.

Используйте родительскую задачу как координирующий контракт общего результата и
интеграционных критериев, не копируя в него подробные критерии детей. Не
делите работу механически на `backend`, `frontend`, тесты и документацию, если эти части
не дают самостоятельного проверяемого результата.

На странице родительской задачи портал рекурсивно показывает текущее поддерево,
ссылки на задачи и их актуальные статусы. Это представление вычисляется из
`parentTask`; не копируйте его в Markdown и не добавляйте поле `Children`.

```bash
toudocu task init ./docs --area AUTH --title "Новый API" --type Feature \
  --parent TASK-AUTH-100
toudocu task tree TASK-AUTH-100 ./docs
toudocu task candidates ./docs --parent TASK-AUTH-100 --format json
```

`task candidates` строит один отчёт для выбора следующей работы. Без
`--parent` он включает все активные `Draft` и `Ready`; с `--parent` — таких
потомков выбранной задачи на любой глубине. Для каждого кандидата отчёт
показывает полноту того же контракта, который проверяет `task ready`,
незавершённые `dependsOn` и итоговый `readyForWork`. Задача готова к работе,
только если её статус — `Ready`, контракт полон, а все зависимости имеют
статус `Done`.

Команда намеренно сохраняет в результате неполные и ожидающие задачи с
причинами, но не выбирает «следующую». `task tree` по-прежнему отвечает только
за декомпозицию, а приоритет и контекст запроса оценивает исполнитель.

## Task Workspace

`work/index.html` — это Task Workspace портала. Доска открывается первой и
показывает `In progress`, исполнимый `Ready`, `Waiting`, `Needs attention`,
`Draft` и настоящий `Blocked`. `Waiting` означает полный контракт Ready, но
незавершённую зависимость; `Blocked` остаётся machine status с текстом blocker.
`Needs attention` показывает вручную переведённый Ready с неполным контрактом.
Эти состояния вычисляются из модели и не записываются в Markdown.

List и Tree используют те же подготовленные данные: Tree следует `parentTask`,
а List удобен для плотного просмотра. Current work перечисляет все задачи
`in-progress`; прогресс берётся только из отмеченных acceptance criteria.
Завершённые, отменённые и архивные задачи свернуты ниже доски, архив сгруппирован
по году. Поиск, фильтры и представление сохраняются в URL. В статической сборке
Workspace остаётся только для чтения. В основном `serve` на loopback-адресе сервер
возвращает допустимые для вычисленного состояния действия и отдельно предлагает доставку
в Agent Console либо переносимый handoff. `Start work` повторно проверяет
digest, готовность и зависимости и переводит задачу `ready → in-progress`.
Ask, Clarify, Continue work, объяснение блокера или проблем и запрос следующего
шага не копируют полный контекст задачи или шаблон инструкции в браузер. Действия
только для чтения требуют `ReadOnlyTurns` при доставке в Agent Console, а handoff
явно остаётся текстовой инструкцией. Установка или обновление
Toudocu skill требует отдельного подтверждения. Drag-and-drop и запуск task
verification здесь не появляются.

Фрагмент созданного дочернего черновика содержит единственный источник связи:

```md
<!-- toudocu
id: TASK-AUTH-101
status: draft
taskType: feature
parentTask: TASK-AUTH-100
-->

# TASK-AUTH-101: Новый API
```

## Обязательные разделы готовой задачи

Начиная со статуса `Готово к работе` нужны:

1. `Результат` — что сможет наблюдать пользователь или система.
2. `Изменение поведения` с точными подразделами `Было` и `Станет` — для
   `Feature`. Название `Станет` является частью формата и не заменяется на
   `Стало`. У бага отдельная структура ниже.
3. `Область изменения` — разрешённые файлы и каталоги.
4. `Не входит в задачу` — явно исключённая работа.
5. `Критерии приёмки` — проверяемые условия `AC-*`.
6. `План` — предполагаемая последовательность работы.
7. `Проверка` — команды для каждого критерия, `ALL` и `DOCS`.
8. `Влияние на документацию` — конкретные файлы либо объяснение, почему правка
   документации не нужна.

Пути в `Области изменения`, записанные в обратных кавычках, считаются
относительно `--repository-root`. Существующий путь должен находиться внутри
репозитория. Новый файл допустим, если существует его безопасный родитель.
Шаблон с `*` обязан найти хотя бы одно совпадение.

## Критерии и команды

Каждый критерий имеет уникальный локальный ID:

```md
<!-- toudocu:section acceptance-criteria -->
## Критерии приёмки

- [ ] `AC-01` Неверный токен возвращает ошибку `INVALID_TOKEN`.
- [ ] `AC-02` Действительный токен позволяет сменить пароль.
```

В разделе `Проверка` для каждого критерия нужна ровно одна строка с хотя бы
одной командой:

```md
<!-- toudocu:section verification -->
## Проверка

- `AC-01` → `go test ./internal/auth -run TestInvalidToken`
- `AC-02` → `go test ./internal/auth -run TestResetPassword`
- `ALL` → `go test ./...`
- `DOCS` → `toudocu check ./docs --strict`
```

| Цель | Что она подтверждает |
|---|---|
| `AC-*` | Один критерий приёмки |
| `ALL` | Полный принятый цикл проекта |
| `DOCS` | Полную проверку документации |
| `QUALITY` | Соблюдение явно связанных стандартов командами самой задачи |

Для готовности нужны все `AC-*`, `ALL` и `DOCS`. Если поле `Стандарты` не
пустое, нужен ещё один `QUALITY`. `task context` добавляет явно указанные
стандарты и runbook в `documents` и `requiredReads`; применимость стандарта по
его области Toudocu не угадывает. У выполненной задачи все `AC-*` отмечены
`[x]`.

## Фактическое влияние на документацию

```bash
toudocu task changes TASK-AUTH-014 ./docs --base HEAD --target working-tree
```

Команда и вкладка «Изменения» сопоставляют пути из раздела `Влияние на
документацию` с текущим Git diff. Сам файл `TASK-*` показывается отдельно как
контракт работы и не увеличивает число постоянных документов. Явно названные
пути важнее связей, вычисленных по модулю, сценарию, процессу, экрану или
контракту.

`declared-document-not-changed` означает, что обещанный файл не изменён;
`undeclared-document-change` — что изменён незаявленный документ. По умолчанию
это предупреждения для человека, а не доказательство ошибки. Начало и конец
сравнения всегда видны; Toudocu не угадывает скрытый начальный коммит задачи.

Флаг `--tree` доступен только для `TASK-*` и включает выбранную задачу и всех
её потомков. `BUG-*` не может быть корнем или частью дерева. Объединённое
влияние сохраняет `declaredBy` для каждого пути, а Markdown всех выбранных
`TASK-*` остаётся отдельным списком рабочих артефактов.

## Дополнительный контракт бага

Баг сначала доказывает наличие дефекта, затем — исправление того же поведения.
Всегда обязательны `Серьёзность`, `Приоритет`, `Воспроизводимость`, `Регрессия`,
`Модуль`, `Сценарий` и `Последнее обновление`.

| Поле | Допустимые значения |
|---|---|
| `Серьёзность` | `Критическая`, `Высокая`, `Средняя`, `Низкая` |
| `Приоритет` | `Срочный`, `Высокий`, `Обычный`, `Низкий` |
| `Воспроизводимость` | `Всегда`, `Часто`, `Иногда`, `Редко`, `Не воспроизводится`, `Неизвестно` |
| `Регрессия` | `Да`, `Нет` |

Серьёзность описывает ущерб, приоритет — порядок работы; одно из другого не
вычисляется. При `Регрессия: Да` укажите версию или период появления.

Даже черновику нужны `Симптом`, `Ожидаемое поведение`, `Фактическое поведение`
и либо `Шаги воспроизведения`, либо `Доказательства`. С «Готово к работе» также
нужны `Причина`, `Область изменения`, `Не входит в исправление`, `План`,
`Критерии приёмки`, `Проверка` и `Влияние на документацию`.

Если причина неизвестна, напишите `Не установлена`, а предположения вынесите в
`Гипотезы`. У выполненного бага причина уже установлена. План бага —
нумерованный список без галочек; галочки остаются у критериев.

Готовый баг содержит критерий регрессионного теста. Если автоматизация
невозможна, раздел `Регрессионный тест` объясняет причину и даёт точный ручной
путь.

Чисто технический дефект может указать `Сценарий: Не применяется`, но тогда
нужен раздел `Связь с пользовательским поведением`. Все названные `MOD-*`,
`UC-*`, `SC-*`, `TR-*` и зависимости должны существовать.

Не помещайте в доказательства пароли, токены, ключи, персональные данные и
необработанные производственные дампы с чувствительными данными.

## Архив

Активные задачи лежат в `work/`, завершённые и отменённые можно переместить в
`work/archive/YYYY/`:

```text
work/TASK-AUTH-014.md
work/BUG-AUTH-021.md
work/archive/2026/TASK-AUTH-009.md
```

Используйте команды:

```bash
toudocu task archive TASK-AUTH-009 ./docs --format json
toudocu task restore TASK-AUTH-009 ./docs --format json
```

Архивируются только «Выполнено» и «Отменено». Команда проверяет статус, пути,
конфликт назначения, входящие ссылки и относительные ссылки самой задачи. Если
ссылка после переноса разрешалась бы иначе, файл остаётся на месте. Содержимое
и статус не меняются.

`task restore` возвращает файл в `work/`. Им можно восстановить и ошибочно
архивированную активную задачу. ID и зависимости действуют во всём `work/**`,
поэтому `task init` не переиспользует архивные номера.

Поле родителя и вычисленные дети также разрешаются через активную часть и
архив. Архивирование одной задачи не перемещает её родителя или детей.

## Диагностика декомпозиции

Автоматизация может опираться на стабильные коды:

- `TASK_PARENT_INVALID`, `TASK_PARENT_UNKNOWN`, `TASK_PARENT_SELF` и
  `TASK_PARENT_TYPE_UNSUPPORTED` — неверное объявление родителя;
- `TASK_PARENT_CYCLE` — цикл дерева;
- `TASK_COMPLETION_CYCLE` — цикл общего графа `Parent` и `Dependencies`;
- `TASK_CHILD_INCOMPLETE` — завершённая родительская задача с незавершённым ребёнком;
- `TASK_CANCELLED_PARENT_ACTIVE_CHILD` — отменённая родительская задача с активным ребёнком.

Сообщение содержит исходный путь, строку метаданных, ID задачи и связанный ID,
когда он известен.

## Полный пример

```md
<!-- toudocu
id: TASK-AUTH-014
status: ready
taskType: feature
priority: high
module: MOD-AUTH
useCase: UC-AUTH-03
flow: FLOW-AUTH-RECOVERY
dependsOn: TASK-MAIL-004
updated: 2026-07-27
-->

# TASK-AUTH-014: Добавить восстановление пароля

<!-- toudocu:section result -->
## Результат

Пользователь может безопасно восстановить пароль по одноразовой ссылке.

<!-- toudocu:section behavior-change -->
## Изменение поведения

<!-- toudocu:section before -->
### Было

Пользователь не может самостоятельно восстановить забытый пароль.

<!-- toudocu:section after -->
### Станет

Пользователь восстанавливает пароль по одноразовой ссылке.

<!-- toudocu:section scope -->
## Область изменения

- `internal/auth/`;
- `internal/mail/`;
- `docs/modules/auth.md`.

<!-- toudocu:section out-of-scope -->
## Не входит в задачу

- изменение правил регистрации;
- новый почтовый провайдер.

<!-- toudocu:section acceptance-criteria -->
```

## Путь от черновика до проверки

1. `task ready` проверяет полный черновик и не меняет статус.
2. После ручного перехода в «Готово к работе» `task context` собирает
   ограниченный набор нужных документов.
3. `task verify --dry-run` показывает точный план команд без запуска.
4. Только после отдельного разрешения `task verify --run` последовательно
   выполняет команды из корня репозитория.

Одинаковая команда выполняется один раз, даже если связана с несколькими
целями. Сбой одной команды не отменяет остальные. Команды считаются доверенным
кодом репозитория и получают права текущего пользователя.

Форматы отчётов и коды завершения описаны в
[CLI-контракте](../contracts/cli.md).
