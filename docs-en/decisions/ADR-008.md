# ADR-008: React Islands and Vite Without Turning Portal into an SPA

Toudocu keeps its multi-page portal with semantic HTML produced by Go. React
19.x serves only application work surfaces and isolated islands, Base UI 1.x
serves complex composable interactions, and Vite 8.x packages assets.

<!-- toudocu:section context -->
## Context

Portal needs one durable foundation for complex interfaces without losing its
standalone static build, nested URLs, or useful content without JavaScript.
Editor, Changes, Discussions, and the Roadmap write operation need state,
focus management, and composable accessible interactions. Moving all of Portal
to React would create a second document-rendering path, client routing, and a
JavaScript dependency for ordinary pages.

The browser runtime combines framework-free TypeScript with isolated React roots
and islands, while Vite packages the assets. This decision records the boundary
of that implemented architecture.

<!-- toudocu:section decision -->
## Decision

The documentation and application models contain no HTML, CSS classes, or
other browser-specific markup. Go decides about Markdown, relationships, Git,
write permission, and page capabilities. Go presentation code turns prepared
view models into safe semantic HTML, JSON, and API responses. The current
placement of some of that code in `internal/app` does not define the
architectural boundary or require package refactoring.

Portal remains a multi-page site without an SPA or React Router.
`appearance.ts`, `portal.ts`, and `serve.ts` do not import React, React DOM, or
Base UI. `screen-map`, `playable-flow`, and `api-docs` remain framework-free.

Two classes of React surface are allowed:

- Editor and Changes are separate page-level application roots. Go creates the
  shell, `PageBootstrap v1`, assets, an empty root, and, when needed, an
  accessible failure state; React owns the DOM only inside the root. CodeMirror
  and CodeMirror Merge own their latency-sensitive state and do not mirror it
  in React.
- Stateful features in canonical `serve` mount only through framework-free
  `IslandHost` and dynamic `import()`. Roadmap starts as an `eager` island and
  Discussions as an `activated` island. A new island needs no ADR while it
  keeps this boundary. A new application-root class, giving React routing, or
  changing the runtime boundary requires architectural review.

`IslandHost.discover()` is idempotent. One island instance has at most one React
root. After fully validating the target page, soft navigation emits
`toudocu:pagebeforechange`, calls `unmountAll()`, replaces `.site-layout` and
`PageBootstrap`, synchronizes assets, then emits `toudocu:pagechange` and
discovers again. Cleanup releases React roots, effects, listeners, requests,
and feature-owned overlays or portals.

A dynamic import, feature JSON, root-creation, or first-render failure affects
only that island. Useful Go-generated fallback content stays outside the React
root. The island receives `data-td-island-state="error"` and a localized
message. An activated island can start again after a new user action; an eager
island retries only after the next `pagechange`.

The mount point contains only the island name, instance, and, when needed, a
reference to `application/json` with an immutable view model. Runtime, locale,
theme, capabilities, permissions, and endpoints come only from
`PageBootstrap v1`. Feature JSON contains no security decisions or absolute
paths and passes minimal feature-specific validation. React uses `createRoot`,
not SSR or hydration.

Native HTML remains the base primitive. Use Base UI when a browser-native
element is insufficient for a composable accessibility and interaction
contract—for example, a dialog, menu, popover, tooltip, select, combobox, or
complex tabs. Ordinary buttons, links, labels, layout, and static elements do
not receive a required Base UI wrapper.

Sources are split into directed layers: `design`, `ui`, `docs-ui`, `features`,
and `entries`. `ui` depends only on `design`; `docs-ui` on `ui` and `design`;
features on lower layers and permitted browser infrastructure; entries compose
features. `design`, `ui`, and `docs-ui` do not read `PageBootstrap`, APIs,
product events, or catalogs through `core`. `docs-ui` receives data, callbacks,
and a translator through props. Automated import checks protect this DAG.

Vite is used only during development and packaging: it provides multiple entry
points, dynamic chunks, relative references, a reproducible manifest, and
separate `static` and `serve` closures. Production resources are embedded in
the Go binary; Node.js is not a runtime dependency. This ADR fixes the React
19.x, Base UI 1.x, and Vite 8.x lines, while the lockfile pins exact versions.
A major update requires architectural review; a new ADR is needed only when
the decision boundary changes.

## Considered options

- React for all of Portal and React Router were rejected: they duplicate Go
  rendering and make documents depend on a client runtime.
- Framework-free TypeScript alone was rejected for complex work surfaces:
  manual state, focus, and overlay handling already creates unnecessary
  implementation complexity.
- React SSR and hydration were rejected: they add a second rendering pipeline
  without a measurable need.
- Base UI for every primitive was rejected: native HTML is simpler and does not
  bind the whole DOM structure to a library.
- npm workspaces and separate packages were rejected until there is an
  independent need for publishing or physical isolation.

<!-- toudocu:section consequences -->
## Consequences

- A regular Portal page keeps content without React and works at the host root
  and a nested URL.
- Complex surfaces get React and Base UI, but do not own routing, the project
  model, or security decisions.
- Soft navigation gets an explicit commit boundary and required island cleanup.
- Go continues to create useful static HTML; a physical presentation-package
  split remains a separate possible refactoring.
- Browser-resource packaging grows more complex because of the manifest and
  dynamic chunks, but the released binary remains standalone.
